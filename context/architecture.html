Part 1

Foundations

The idea

Why this app exists

Every cycling map tells you a hill exists. None of them tell you which way it hurts.

A street that is a pleasant coast heading south is a grind heading north. Existing maps collapse that into one number. This app keeps the two apart: it stores a separate elevation profile for each direction of travel, and draws two coloured lines per street, one for each way.

The second idea: riding a street again makes the data better, not just newer. Every stored height is an average over every pass ever made over that spot, so the fourth ride down a street nudges the number toward the truth instead of replacing it.

Everything else in this document is machinery in service of those two ideas.

For feature design · who it serves today

One rider (Julian, who owns the project), one Android phone, one city. The street map covers central Colorado Springs, the northwest suburbs and Ute Valley Park. The system is built so more riders could be added later without a rewrite, but a stored ride carries no rider identity today, so two riders' data could not be told apart. Every line on the map comes from one person's rides: as of 11 October 2026, through ride 89, 49 usable rides, which have drawn 958 lines across 751 blocks.

How the pieces talk to each other

The three programs (the phone app, the server, and the scripts that import the street map) never call each other's code directly. The phone talks to the server by sending it web requests. The server and the import scripts both talk to the same Postgres database. Nothing else connects them.

Databases in five minutes

Everything you need to follow the rest

A database is a set of tables. A table is a grid, like a spreadsheet tab: named columns across the top and one row per thing it stores.

The segments table has one row per block of street (Part 2 explains the word "segment"). Its columns include street_name, length_m, bearing_deg (which way the block points) and geom (its shape). Here are three real rows out of 66,684:

null means "there is no value here": the box is empty. It is different from zero and different from an empty word. Zero is a number; null is the absence of one.

In the table above, row 22300 has street_name = null: that footway has no name in OpenStreetMap. Canonical, and folding a sidewalk

"Canonical" is the code's word for "the line that counts". A canonical segment is one that rides are matched against and that can be drawn on the map.

A sidewalk that OpenStreetMap maps as its own path is folded into the road beside it: its canonical_segment_id points at the road, and from then on it is never matched or drawn. A rider on that sidewalk still counts, because the road a few metres away is matched instead. Of the 66,684 segments, 46,271 are canonical and 20,413 are folded. Flow A in Part 7 explains how a path qualifies.

So one rule runs through the whole system: only segments whose canonical_segment_id is null are matched against rides or drawn. A sidewalk pointing at a road is ignored; the roads, trails and paths that stand on their own are what count.

Row, and why it matters here

A row is one entry. Ten rides over one spot leave one row, not ten: the database does not store ten separate measurements of that spot. It stores one entry holding the average of all ten, plus a count of how many went into it.

Merging a ride

Blending a ride's measurements into the stored averages. For each spot the ride passed:

new average = (old average × old count + new reading) ÷ (old count + 1)

Once that runs, the old average is gone, overwritten by the new one. The individual reading cannot be recovered afterwards, which is why a merged ride cannot be taken back out. Older project notes call this "folding a ride in"; this document keeps the word "fold" for sidewalks only.

Part 2

One block, end to end

The block itself

Real data · segment 12555

Everything from here to the end of Part 2 follows one real block: South Wahsatch Avenue, database id 12555. It runs almost due south, is 104.4 metres long, and has been ridden 4 times southbound and 5 times northbound. It is a good example because it renders a different colour in each direction.

Step 1 · The segment

The unit the whole system is built on

Segment

One block of one street. Not the whole street: just the piece between two intersections. South Wahsatch Avenue runs for well over a kilometre and is stored as many segments, one per block.

OpenStreetMap supplies a "way": a line that might run the whole length of the street. The import scripts cut it wherever it touches another way they kept, and cut any piece longer than 150 m, because sidewalks and trails can run for hundreds of metres without an intersection. Each resulting piece becomes one row.

Each segment row stores three things that need explaining:

geom · a LineString

An ordered list of map coordinates, joined by straight lines. That is all a LineString is. Segment 12555's is four points long (longitude, latitude):

[-104.81843, 38.82638] → [-104.81845, 38.82591] → [-104.81846, 38.82578] → [-104.81847, 38.82544]

Four points, three straight hops between them. That is enough because this block is nearly straight; a curving trail needs many more points to trace its bends.

length_m

How long the block is, in metres, measured along that line. Here: 104.4.

bearing_deg

A compass heading, 0 to 360°, for the straight line from the first point to the last. 0 is north, 90 east, 180 south, 270 west. Segment 12555's is 182°, almost exactly south.

It is still stored, but since 1 September 2026 nothing uses it to judge which way a rider was going. The server now compares the rider with the street's direction at the rider's own position, which matters on curving trails (Part 5, "Picking the right street").

Why two colours can appear before an intersection

The coloured pieces on the map are not segments, and they are not what gets cut at intersections. A single 104-metre segment is normally painted as six separate coloured pieces. Part 3 explains this properly.

Step 2 · GPS fixes and their heights

What the phone actually records

GPS fix

One ping: a single moment where the phone reports where it thinks it is.

The app asks Android for a fix every 1 to 4 seconds, picking the interval from the current speed with the aim of one fix every 11 metres. In practice Android delivers them every 1 to 2 seconds whatever is asked. Measured over all 36,266 stored fixes, riding slower than about 22 km/h produces a fix every 5 to 6 metres, and riding faster one every 12.

Where the height comes from

The phone has two ways to know its height. GPS altitude is a satellite estimate that jumps around by metres from one second to the next. The barometer measures air pressure, which drops steadily as you climb, so it tracks small changes in height far more precisely. Measured on the stored rides, the barometer is off by about 0.3 m per 15-metre stretch of street against about 0.65 m for GPS. On slope, that is roughly 2% of error against 4%: a whole colour band.

The barometer's weakness is that it only measures change. It knows the rider has climbed 6 metres since the start; it does not know how high the start was. So each fix's height is built from two parts:

height of a fixGPS altitude of the ride's first fix
plushow far the barometer says the rider has climbed since then

The first part carries the GPS error, typically 10 to 20 metres, and it is the same for the whole ride. Part 5's DEM anchor, a correction against official terrain heights, removes it once the ride reaches the server. If no fresh barometer reading exists for a fix, the fix falls back to plain GPS altitude and is labelled gps.

The barometer is read by the native module from Part 1's table, which keeps running while the screen is locked. Until 3 October 2026 the app used a stock sensor library that quietly stopped the barometer 11 to 19 seconds after the screen locked; every height after that was GPS. One ride left locked in a pocket got 93.5% of its heights from GPS.

For feature design · the barometer can be checked

During a ride the screen shows one health line: whether the sensor is alive, and what share of recent fixes got a barometric height (for example "Barometer 100% of fixes, 5.0 Hz", where Hz means readings per second). After a ride, npm run verify-barometer grades it. alive is a pass. stopped means some stretch of 30 seconds or more fell back to GPS. unmeasured means half the ride or more produced no fixes, so it could not testify either way. claimed-but-stuck means fixes were labelled barometric while their heights barely changed. Every ride from 84 to 88 graded alive.

The native module is Android-only. An iPhone build would fall back to the stock library and lose the barometer whenever the screen locks.

Fixes are written to the phone's storage as they arrive, not held in the app's memory, because Android can shut the app down mid-ride and relaunch it just to deliver a fix. Nothing goes over the network until the rider presses Stop and the ride is saved.

Step 3 · The run

Grouping fixes by street

Run

The group of consecutive fixes that all landed on the same segment, going the same way.

Ride five blocks down South Wahsatch and you produce five runs, one per block. Turn around and ride back and you produce five more, this time marked backward.

Direction: forward and backward

Not north and south. Forward means travelling from the segment's first stored point toward its last. Backward is the other way.

For segment 12555 the first point is at the north end, so forward = southbound and backward = northbound. On the next street over it might be the reverse: it depends only on which way the OpenStreetMap contributor happened to draw it.

Each segment also stores start_node_id and end_node_id: the identifiers of the points where the block begins and ends. Two segments that share a node id meet there, which is how the server knows which blocks connect.

Step 4 · Buckets

Rounding every ride onto shared positions

Here is the problem buckets solve. Ride this block in August and again in October, and the fixes land in different places both times, because GPS never repeats exactly. Two measurements never taken at the same place cannot be averaged directly.

So they are rounded to shared positions, the way prices are rounded to the nearest dollar so they can be compared.

Bucket

A marked position every 15 metres along a block, holding one height.

Segment 12555 is 104.4 m long, so in each direction it has buckets at 15, 30, 45, 60, 75, 90 and 105 metres from where travel enters the block: seven of them. Every fix is filed under its nearest mark, and the heights one pass files under a mark are averaged. A bucket at 0 only appears when a fix lands within 7.5 m of the start.

A bucket is invisible. Nothing is drawn at it on the map. It is a storage slot.

Where a bucket sits on the real map

On the ground, southbound bucket 45 is a specific spot: 45 metres south of the north-end intersection, on the centreline. Someone with a tape measure could find it. It has no width, and nothing is drawn at it: it is a filing position, like a shelf label.

Is it one grid laid over the whole map?

No. There is no city-wide grid, and nothing is measured from a common origin. The 15 m spacing is one-dimensional and belongs to a single segment: each segment carries its own ruler that starts at zero at its own end and counts along its own centreline. Two segments meeting at an intersection each have their own zero, a few metres apart, pointing different ways.

So bucket 30 on South Wahsatch and bucket 30 on East Fountain are not related, not aligned and not near each other. The number only means something once you say which segment, which is why a bucket row is identified by (segment, direction, distance) and never by distance alone.

Step 5 · The running mean

How several rides become one number

Southbound bucket 45 in the figure above holds 1823.66, from 4 passes. That single number is the average of four separate passes. Here is how a bucket gets there, one pass at a time. The readings are illustrative; the database keeps only the result.

PassReadingStored afterCountArithmetic
1st1823.901823.901the first one, stored as it is

3rd1823.751823.653(1823.60×2 + 1823.75) ÷ 3

The count is passes, not rides and not fixes. Each time a run crosses a mark it adds one reading (the average of its own fixes there) and adds one to the count. A ride that covers the same block twice in the same direction adds two.

Note what is not stored: the four individual readings. Only the average and the count survive. That is why a ride cannot be removed from the model: reversing the arithmetic would need the original reading, and it is gone.

But nothing is actually locked

The raw fixes are never deleted. Every fix from every ride is still in session_samples, the table of raw rides. The bucket averages are only a summary computed from them.

So changing the bucket size from 15 m to 20 m, or how heights are smoothed, is entirely possible. Change the code and run npm run rebuild-model, which throws away every summary and recomputes it from the original fixes. Nothing is lost. The model cannot be nudged in place; it has to be rebuilt whole. Slope and colour are the exception: they are worked out fresh every time the map is drawn, so changing them needs no rebuild at all. A rebuild rewrites the live map, so it only runs with Julian's go-ahead (Part 6, "What a change costs").

Step 6 · Coverage

Where the paint starts and stops

Buckets say how high the road is at seven positions. They do not say how much of the block was ridden, and those are different questions.

Coverage

Two numbers per direction: where riding on this block started, and where it ended, in metres along the block. For segment 12555 both directions are covered from 0 m → 104.4 m: the whole block.

It exists so the map knows where to start and stop painting. Buckets cannot answer that, because they sit on a fixed 15 m grid: the first bucket is at 15 m even when the rider entered the block at 0.

Painting from the first bucket instead left a small unpainted stub at the head of nearly every line, and the map looked like a dashed route rather than a continuous one. Recording where the riding really started fixed it.

Coverage only grows. Ride the first half of a block one day and the second half another, and the two ranges are combined into one. Since 29 September 2026 a line is also drawn right up to an intersection the rider rode through, even when no fix happened to land in the last few metres before it (Part 5, "Drawing to the junction").

Both directions independently agree the north end is higher, by about a metre. Ridden south it is a gentle descent; ridden north, a gentle climb. That is the whole idea of the app, visible in one block of real data.

The two directions now also agree on how high the ground actually is. At the same spot, the southbound and northbound heights sit between 0.1 and 1.1 m apart, half a metre typically. In August, when the previous edition of this document was written, they were about 2 m apart.

That opposite-running ruler is how one stored shape serves two independent profiles. One shape is stored in the database. Two separate sets of heights hang off it, measured from opposite ends and drawn on opposite sides.

For feature design · which side a line is on

The side is a drawing convention only. Where across the road the rider actually was plays no part: a rider going south on the wrong side of the road, or on the sidewalk, still counts toward the southbound line, because direction is judged from movement and not from position across the street (Part 5, "Picking the right street").

Part 3

The big misconception

Coloured pieces are not buckets

Read this one twice

A natural first guess is that each coloured piece on the map is a bucket. Segment, bucket and coloured piece are three different things, and keeping them apart makes everything else click.

Two different things called a "line"

"The line" means two different things in this project, and the difference matters later. The stored line exists before anyone rides anywhere.

The stored line · segment geometry

The list of coordinates from Step 1, downloaded from OpenStreetMap and kept in the geom column of the segments table. It exists for every street and trail in the map area, whether or not anyone has ever ridden there. It is used geometrically: how far is this fix from that line, and where along it does the fix land.

The gradient line · what gets drawn

The coloured thing on the map. This one is built from rides: buckets, slopes, colour bands. It is drawn alongside the stored line, offset to one side so both directions are visible at once, and only over the stretch that was ridden.

How the colour of each piece is decided

Not by comparing two neighbouring buckets: that turned out to be too noisy. One slightly off reading can swing the result by a whole colour band, which is why a flat street once came out speckled with oranges and blues.

Two words first: gap, and window

A gap is the stretch of street between two neighbouring buckets. Buckets sit every 15 m, so a block with buckets at 15, 30, 45, 60, 75, 90 and 105 has six gaps between them. A gap is a piece of ground, 15 m long, and it is exactly the piece that gets painted one solid colour. That is what a coloured piece is: the same "six pieces from seven buckets" the figure above shows.

Every gap gets its own colour. Nothing is left out; the whole ridden stretch is covered by gaps laid end to end, and the first and last pieces stretch out to where the coverage starts and ends. Each gap's colour is decided on its own, which is why they are described one at a time.

A window is the set of buckets consulted to decide one gap's colour. It is not a piece of ground and nothing is drawn at its width: it is purely "which stored heights are read to work out how steep this 15 m piece is". The window is deliberately wider than the gap it decides, and the rest of this section is about why.

What a best-fit line is

Picture the buckets on a chart: their positions along the bottom, their stored heights up the side. Six dots. Infinitely many straight lines could be drawn across them, and none of them passes through all six, because the heights are measurements and measurements wobble.

A best-fit line is the single line that comes closest to all six at once. "Closest" needs a definition, and the usual one is least squares: for each dot, measure the vertical distance from the dot to the line (call it the miss), square it, and add up all six. The best-fit line is the one where that total comes out smallest: the least total of the squares.

Squaring does two jobs. It stops a miss above the line cancelling a miss below it, and it makes one large miss cost far more than several small ones, so the line is pulled toward the crowd rather than toward any single odd reading. The slope of that line is the number the colour comes from.

Why six dots instead of two

Which six, exactly

The window reaches two buckets beyond each end of its gap. For the gap from 45 m to 60 m that means buckets 45 and 60 themselves, plus 15 and 30 before, plus 75 and 90 after: six buckets covering 75 metres of street, used to colour 15 metres of it. Move to the next gap and the window slides along with it, so neighbouring gaps share most of their buckets. That overlap is why colours change gradually along a street instead of jumping.

Finally the result is capped at ±25%: no street or trail here averages anything steeper over the 75 m a window reads, so anything beyond that is a bad reading, not terrain. Then the slope picks one of six bands:

≤ −8%plunge
−8 to −3descent
−3 to 0easy down
0 to +3easy up
+3 to +6climb
> +6%wall

Each band includes its upper edge: exactly 0% is green, exactly +3% is yellow.

What these percentages feel like

First, a trap in the numbers. Heights like 1823 m are altitude above sea level, not climb. Colorado Springs sits at roughly 1,800 m (about 5,900 ft), so every height in this database starts near that. A change from 1822 to 1824 is a 2-metre rise, and on its own that says nothing about steepness.

Slope is rise divided by distance travelled forward. The same 2 m rise is a 13% wall if it comes over 15 m of street, and a gentle 2% over 100 m. The percentage is the only thing that describes steepness; raw heights never do.

The percentage is also unit-free: 6% means 6 metres up per 100 metres forward and 6 feet up per 100 feet forward. Some reference points:

GradeSomething you know at that grade
2 to 3%Barely perceptible; you notice it in your speed, not your legs
6%The steepest a US highway normally goes before runaway-truck ramps appear
8.3%The legal maximum for a wheelchair ramp
7 to 9%The average grade of a famous Alpine cycling pass, sustained for an hour
15 to 25%Mountain-bike trail pitches; walking territory for most riders
For feature design · the red band is open-ended

Sustained 6% is a real climb on a bicycle, so painting it red is defensible. But everything above 6% is the same red, so a 7% street and a 20% trail pitch are drawn identically, right up to the ±25% cap. That was a fine simplification for a city grid where almost nothing passes 8%; on mountain trails it throws away most of the interesting range. Splitting red into two or three bands is probably the cheapest visible improvement available: colours are computed fresh on every map request, so it needs a server change and no rebuild.

Part 4

The three programs

Who does what

Now that the vocabulary exists

First: one word, two meanings

segments is a table in the database: where street shapes are stored, written by the import scripts.

/segments is a web address on the server: the phone sends a request there meaning "give me the coloured lines for this part of the map". It reads from that table, but it is not the table.

The leading slash is the tell: anything starting with / in this document is a web address, not storage.

"Run by hand"

The import scripts are not a server, and nothing starts them automatically. They are five small programs in the osm-pipeline/ folder ("pipeline" because each feeds the next). Someone opens a terminal, types npm run fetch, and it does its job and exits, like running a spreadsheet macro rather than a website. They are run rarely: only when the map area grows or the rules for cutting streets change.

The web addresses the server answers

These are the server's whole public surface: the phone uses nothing else. In the table, :id stands for a ride's number. POST sends something to the server, GET asks it for something, and DELETE asks it to remove something.

POST /sessions/:id/samplesthe phone, on saveStores a batch of fixes. The phone sends a ride 125 fixes per request, so a stalled connection costs one piece, not the ride.

The split that actually matters

Front end versus back end here is not "screen versus server". It is measurement versus interpretation.

The phone is a sensor with a screen. It records what it observed, keeps it safe, and draws whatever it is handed. It holds no opinion about what a street is; its only geography is measuring how far a ride got from its starting point and cutting lines into coloured pieces for display.

Every judgement lives on the server: which street the rider was on, which way they were going, whether they really rode it, how steep it is. Those need the whole street network and the history of every earlier ride, and neither fits on a phone.

Part 5

The judgement calls

What a heuristic is

The word for most of what follows

Heuristic

A rule of thumb that is usually right, used where being certain is impossible.

"If a fix is within 25 metres of a street and moving along it, assume the rider was on that street" is a heuristic. It is not a proof, and sometimes it is wrong. It is used because there is no way to know which street the rider was on: GPS is fuzzy, streets run parallel, and the phone cannot see.

Every heuristic here has a threshold number attached. Since September every one of those numbers has been chosen the same way: replay every stored ride through the real server code at several values, and count what changes on the map (Part 6, "How a change is measured").

They are explained below in the order that builds the vocabulary. The order they actually run in, on every save, is in Part 7: drop impossible fixes, smooth the heights, match each fix to a street, rejoin fragments, measure each run, apply the gate, draw to the junction, anchor the ride, merge.

Throwing out impossible fixes

The first thing that happens to a saved ride

Two filters run before anything else, each removing single fixes that cannot be real. Both drop a fix rather than repair it: a repaired fix would be a position or a height the rider never reported.

  1. Impossible speed

    A fix is dropped when reaching it from the fix before and leaving it for the fix after would both need more than 20 m/s (72 km/h). One fast leg alone is not enough: that is what an ordinary gap in the recording looks like. Both legs fast means the fix itself jumped, typically a GPS signal bounced off a building.

  2. Impossible height

    A fix is dropped when its height disagrees with its neighbours by more than a 100% grade (one metre up per metre along), measured over the shorter of the two hops either side. The steepest rideable trail here is well under 40%, and a genuine rocky pitch of 45% over a few metres still has to survive, which is why the limit sits as high as 100%. When the limit was set, only 1.6% of the steps between fixes passed 100%, and those are unmistakable: 1971.0 → 1984.1 → 1962.9 m across 4.4 m of ground, a 13 m climb and a 21 m drop in the length of a bike.

Positions are checked first because the height test divides by the distance to the neighbours, and a fix claiming to be 300 m away would distort that judgement for the fixes either side of it.

For feature design · bad signal does not draw lines

A car park, a tall building or a tunnel can throw a fix hundreds of metres away, and the trail on the phone's screen will show the jump, because the screen draws raw fixes. The speed filter removes the jump itself. Anything that survives still has to pass the street matching and the traversal gate below, which is why a spike seen on screen during a ride does not become a line on the map.

Smoothing the heights

One ride on its own, no outside data

Phone barometers are noisy one reading at a time, so right after the filters each ride's heights are smoothed: every height is replaced by a weighted blend of itself and its neighbours in time. Nothing outside this one ride is consulted.

Until 24 September 2026 the blend only looked backwards in time (a one-pass "moving average"). That had a cost: the height it reported for a spot was really the height of ground some way back along the ride, between 11 and 27 metres back depending on speed. Ride the same hill fast and then slowly, and the two passes disagreed by about a metre on a 6% grade and 1.9 m on 12%. The error always ran the same way, so averaging more rides could not remove it.

The fix runs the same blend forwards through the ride and then backwards over the result. The second pass carries the mirror image of the first pass's delay, so the two cancel exactly; engineers call this zero-phase smoothing. The blend's strength was re-tuned so the noise reduction stayed exactly where it was.

An open question about it

Three measures judge the elevation model (Part 6, "How a change is measured"). Two of them, agreement with official terrain heights and agreement between rides, say the new smoother is better. The third, consistency within a single ride, says it is slightly worse: 1.46 m before, 1.58 m after. Whether that measure already disagreed when the smoother shipped is still to be checked.

The traversal gate

"Did you actually ride this, or just touch it?"

The problem, concretely

A rider goes east along East Fountain Boulevard and crosses South Institute Street. For a second or two they are physically in that intersection, so a GPS fix lands there, genuinely within a few metres of South Institute Street.

The server sees a fix on South Institute Street with a height, and paints a 139-metre gradient line down a street nobody rode. Before this rule existed, five such phantom lines were visible on the map.

The fix, built up slowly

The test is: did this run cover any ground along that street? Answering that needs one more term.

Distance along

A GPS fix is a point somewhere near the street, never exactly on the stored centreline: the centreline is a drawn line and the fix is a noisy measurement. Distance along throws away how far to the side the fix landed and keeps one number: how far down the segment it sits, measured from the segment's start.

On South Wahsatch, which runs north to south, the start is the north end. A fix that lands 40 metres down the block has a distance along of 40 m whether the fix itself was 2 metres off the centreline or 12.

Sideways distance belongs to an earlier step: the matcher uses it to decide which street a fix belongs to, and once that is decided it plays no further part. Only distance along and height go into the elevation model.

The computed sideways distance is never written down, but it is always recoverable: the raw fix, its latitude and longitude, is kept forever in session_samples. A rebuild re-reads the raw positions and recomputes every distance from scratch, which is the whole reason a matching decision made months ago can be revisited after a rule changes.

Span

Within one run: the largest distance along, minus the smallest. Mark every fix of the run on the ruler above and measure from the leftmost mark to the rightmost. That width is the span.

It is built out of fixes, so it inherits their spacing. In the figure above, the first fix landed 9 m into the block and the last 95 m in, so the span from the run's own fixes is 86 m, not the block's full 104.4 m. In practice the two fixes just outside the run usually close that gap; they are explained below as "bracketing fixes".

Span belongs to one run, not to the segment. The gate judges runs one at a time, and a segment collects many runs over many rides. The segment's own length enters in one place only: the gate has a second test, explained just below, that divides the run's span by the segment's length to get the share of the block it covered, so 86 m on this 104.4 m block is 82%. (That share is not Step 6's coverage, which records where along the block riding started and ended over every ride.)

It is not the distance travelled, and it is not how many fixes there were. A run of eighty fixes that never moved has a span of nothing. The three rows below are the same 104 m block, drawn to the same scale.

So the rule becomes: keep the run only if its span is at least 25 metres, or it covers at least 70% of the block. Two tests, because neither works alone: a plain 25 m rule throws away genuinely ridden short connector pieces, and a plain percentage rule lets a touch on a very short segment through.

Why one fix has a span of zero

Span is a difference between the furthest and the nearest. If a run contains only one fix, the furthest and the nearest are the same fix, so the difference is zero: 40 − 40 = 0.

That broke real crossings. Riding across a 10-metre stub of trail might produce exactly one fix on it: one fix, span zero, rejected. Twenty-three legitimate lines disappeared this way in a single ride, showing up as gaps.

Bracketing fix

The fix immediately before a run starts, and the one immediately after it ends: the bookends around it.

These are fixes from outside the run. The server holds the whole ride as one list of fixes in time order, and a run is a stretch of that list. The bracketing fixes are simply the list entry before the stretch and the one after it. What they were doing does not matter: one may belong to a run on a different street, one may have matched nothing at all.

How they are used: each is dropped onto this segment the same way as any other fix (clamped to the segment's ends if it falls past them), and the two landing points are allowed to stretch the span. Their heights are never read: they widen the measurement without adding a single height to the model, which is correct, because they were recorded somewhere else.

This solves two problems at once. Short crossings: a 10-metre trail stub gets one fix or none, but the bookends sit either side of it, one landing at 0 m and the other at 10 m. Span 10 m: kept. Phantom lines: riding past a cross street, the bookends are on the street being ridden, and dropped onto the cross street they both land at nearly the same point. Span near zero: rejected. The bookends cannot resurrect a phantom, because they sit on the wrong street the whole time.

Re-measured 11 October 2026: the gate stays at 25 m / 70%

Lower thresholds were tested against every stored ride, using an independent check of what was really ridden (the "witness", defined in Part 6). The runs a lower gate would let in are mostly genuine riding. But the new lines they would add come to only 72 to 306 m across 260 km, and some of them would be duplicate paint: a second line on a path beside a street that is already drawn, so the same riding shows twice. Count those as harmless and the best setting gains 130 m; count them as a cost and it loses 76 m. Too little either way to justify a rebuild. Today the gate rejects 4 genuinely ridden passes, 179 m in all, across every ride.

Picking the right street

Map matching

Map matching

Working out which street each GPS fix belongs to, and which way the rider was going along it. The part of the server that does it is called the matcher.

For each fix the matcher applies five rules, in order.

  1. Throw out fixes that cannot be placed

    Accuracy worse than 30 m: the phone itself says it could be 30 metres off, which is wider than the gap between parallel streets. No direction: direction is worked out from the rider's movement (rule 3), and a rider who moved less than 6 m between the fix before and the fix after, such as one waiting at a light, has no direction worth trusting.

  2. Find nearby candidates

    Every street whose centreline comes within 25 metres of the fix is a candidate. This is purely a distance filter: the rider could be on this street or on another one nearby.

  3. Check the rider was moving along it

    The rider's direction is the compass bearing from the fix before to the fix after. The street's direction is measured where the rider is, over 10 metres either side of the fix, not from one end of the segment to the other. Within 45° of each other: riding forward along it. Within 45° of the opposite: riding backward. Neither: crossing it, so it is dropped as a candidate.

  4. Prefer to stay where you already are

    A street and its separately mapped sidewalk sit 5 to 10 metres apart, inside GPS error, so picking the nearest street for every fix on its own made one ride flip back and forth between them. Once a run is established, a rival street has to be more than 8 metres closer to take over. A genuine turn onto another street still wins.

  5. Prefer streets that connect

    A candidate that does not touch the street the rider was just on (the two share no node) has to be 6 metres closer to win. It is a nudge, not a ban: where nothing nearby connects, such as a gap in the map or a car park, every candidate carries the same handicap and it cancels out. The last matched street keeps vouching for its neighbours for 15 seconds, a couple of dropped fixes' worth.

Fixes that pass become runs: consecutive fixes on the same street, going the same way.

Why direction comes from movement, not from the phone

Until 1 October 2026 the direction was the heading the phone itself reported. Tracing every stored ride that went out and back along the same street showed that the phone's heading was what got directions wrong. Working direction out from where the rider actually moved misses 30 genuinely ridden passes across all rides, against 47 with the phone's heading (re-measured 11 October). "Misses" means the map does not show the pass on the line for the direction ridden: 26 of the 30, 1.24 km in total, show up on the opposite direction's line instead, and the gate rejects the other 4 (Part 6, "What a lost pass looks like").

Why the street's direction is measured locally

The old test compared the rider with the straight line from one end of the segment to the other (bearing_deg from Step 1). On a street, that line is the street. On a switchback trail it describes no part of the trail: a rider correctly on it can be heading 90° away from that end-to-end line, so the trail was dropped as a candidate and one descent arrived as fragments. Singletrack was losing about a third of its runs, against 16% on streets. Since 1 September 2026 the test uses the trail's direction at the rider's position.

The limitation, and the decision about it

This matcher is greedy: it decides fix by fix and never revisits a choice. The textbook alternative (a "Viterbi" matcher, which picks the most likely route for the whole ride at once) was measured on 3 October 2026 and rejected. At 45 of the 47 places where a ride appeared to jump between streets that do not connect, the street map itself is missing the join: two trails meet on the ground, but OpenStreetMap records two separate end points close together (4 m apart in one case examined). A whole-ride matcher would refuse those real movements outright, and the most it could gain was 28 metres of road.

So the decision was to repair the map's connections instead. That repair, treating street ends within a few metres as one junction, was built and measured: it fixes how the map records which streets connect, but moves the drawn map by 70 m in 225 km, so it is left switched off.

Rejoining fragments

Runs on one street, in one direction, under 45 seconds apart

A traversal can still arrive in pieces: a burst of bad fixes, a moment matched to a path beside the trail, a fix the phone never delivered. Each piece is its own run, and the gate judges runs one at a time, so a 146-metre descent broken into five pieces of 1 to 15 m would be thrown away five times.

So before the gate sees them, runs on the same street, in the same direction, less than 45 seconds apart are joined back into one. When this was built, the pieces of one traversal were measured at 0 to 45 seconds apart (49 of 51 cases), and separate crossings of the same trail at least 90 seconds apart, never in between.

What stitchFragmentedRuns actually does

(stitchFragmentedRuns is the code's name for this step.) It does less than the name suggests. It walks the runs in time order, remembering the most recent run seen for each pair of street and direction. When a new run turns up on a pair it has seen before, it checks exactly one thing: how many seconds passed between the previous run's last fix and this run's first fix. Under 45, it appends this run's fixes to the previous run. Over 45, it starts a fresh one.

Because appending moves the previous run's end time forward, the next piece is measured against the new end. That is what lets five pieces chain into one run instead of merely joining in pairs.

Three things it does not do

It does not change any direction. Every piece already had "forward" or "backward" stamped on it when it was matched, and only pieces that agree on street and direction are joined. Two pieces pointing opposite ways stay separate however close in time.

It does not rescue fixes that failed to match. Fixes recorded between the pieces stayed unmatched and contribute no height to anything.

It cannot join pieces on different segments. When a traversal breaks across two neighbouring segments, there is nothing to join by street and direction.

So what does it actually recover?

Extent, not data. Five separate runs meant five separate spans of 1 to 15 m, each judged alone and each failing the 25 m minimum. Joined into one run, the first fix sits near the top of the descent and the last near the bottom, so the span is the full 146 m and the gate keeps it. The heights that reach the buckets are exactly the ones the five pieces already had; the only change is that the gate measures all five together, which is why rejoining has to happen before the gate.

When it shipped in August it cut rejected fragments from 75 to 2, while genuine intersection touches stayed rejected (94 before, 92 after). Re-measured on 4 October 2026, a 90-second window would add 249 m of drawn line, 214 m of it on ground the independent check could not confirm, and not one new line; 45 s stays. The gate losses that remain are not unjoined fragments either: each is a single run, and where a traversal does break, it breaks across segments, which joining by street cannot reach.

Drawing to the junction

Finishing a line at the intersection the rider came through

Coverage (Part 2, Step 6) records where along a block the riding started and ended, measured from the fixes. Fixes are 5 to 12 metres apart, and the matcher deliberately holds a rider on the old street for a fix or two past a corner (rule 4 above), so the first fix counted on a new block usually lands some metres in. Lines used to stop short of intersections the rider had just ridden through. Measured across the archive, that left 6,885 m of road unpainted, 3,951 m of it at the artificial cuts the import makes every 150 m, which is why gaps showed up where there was no junction at all.

Since 29 September 2026: if the fix just before a run was on a street that physically meets this block at the end the rider entered from, within 15 seconds, the line is drawn all the way to that end. The same goes for the fix just after a run and the far end. Nothing is invented: no bucket is added and no height guessed, only the extent the route already implies. The gate still judges the run's own span, so this can only lengthen a line that was already accepted; it can never turn a rejected run into a drawn one.

A gap in the buckets is not a hole in the line

140 lines have a bucket missing somewhere in the middle. The drawing spans the gap, so nothing on the map is blank there (checked on 30 September 2026).

The DEM anchor

Setting each ride's absolute height

The problem, in one analogy

Imagine measuring a staircase with a very precise ruler that has no zero mark. You can say with confidence "each step is 18 centimetres taller than the last". You cannot say how high the bottom step is above the ground.

That is a phone barometer. It measures changes in height well, because air pressure drops as you climb. But it has no idea what absolute height it started at; that depends on the weather.

So, as Step 2 showed, each ride takes its starting height from the GPS altitude of its very first fix. That one reading carries 10 to 20 metres of error, and the whole ride is measured relative to it, so the whole ride is wrong by the same amount.

Why that breaks the map

A constant error would be harmless if every ride made the same one. They do not. Four early rides over the same streets sat 13.20, 13.35, 14.85 and 16.54 metres away from the true ground height: a spread of 3.3 m.

Now average those together in the buckets. Where a ride that thought it was low meets a ride that thought it was high, the running mean welds two profiles that disagree by metres, and an invented step appears in the road exactly at the seam. This is not hypothetical: today 3,470 of the 6,114 buckets (57%) blend more than one pass.

DEM: Digital Elevation Model

A published survey of how high the ground is, everywhere. This one comes from the US Geological Survey, sampled every 10 metres across the country.

It has the opposite strengths from a barometer: absolute heights that never drift, but coarser detail. It does not know about a small dip in one block.

The fix: use each source for what it is good at

Take the barometer's shape (the hill it traced, right except for one constant offset) and the DEM's level (the official height of the ground). After every run in a ride has been measured, and before any of it is stored:

  1. Look up the terrain. For every bucket the ride produced, ask the DEM how high the ground is at that spot on the street's centreline. Each answer is cached forever, because terrain does not move.
  2. Measure the differences. For each bucket, subtract the terrain height from the ride's height. That gives a list of offsets.
  3. Find the middle offset. Line the offsets up in order of size, smallest to largest, ignoring where along the ride each came from, and take the one in the middle. That is the median, and it becomes the single offset for the whole ride.
  4. Shift everything. Subtract that one offset from every height in the ride, then store it.

Worked example. A ride measures five spots as 1814, 1846, 1815, 1812 and 1816 m. The terrain says those spots are 1800, 1801, 1801, 1800 and 1801 m. Subtracting gives five offsets, and one of them is clearly wrong:

as recorded, in ride order+14   +45   +14   +12   +15
sorted, smallest to largest+12   +14   +14   +15   +45
the middle one is the median+14

Every height in the ride then drops by 14 m. The +45 would have dragged an average up to +20, which would have pushed the whole ride 6 metres underground. Sorting and taking the middle gives that bad reading the same weight as any other single reading, one vote, however absurd its value. That is the whole reason for the median over the average.

Four guards keep it honest:

  • One number per ride, never per street. One offset for all rides on a street would assume the street is flat, and the fit would swallow its real climb along with the error. Fitting per ride leaves the real shape alone.
  • The middle value, not the average. One fix under a bridge or one bad terrain sample cannot drag a median, as the example shows.
  • Fewer than 10 terrain points: no anchor. With so little overlap the fit would be fitting noise, so the ride is stored on its GPS level instead. An uncorrected height beats a confident fit to nothing.
  • More than 60 m off: refuse. An offset that large means a broken ride or a place the terrain survey does not cover, not ordinary GPS error. Hiding it behind a wrong anchor would be worse than leaving it visible.
Privacy, worth preserving

Only street coordinates from OpenStreetMap, public data about where roads are, are sent to the terrain service. Ride traces never leave the server and the database.

What the anchor cannot fix

One offset per ride cannot remove drift within a ride: the barometer's zero sliding slowly as the weather changes over an hour of riding. A correction for that, nick- named "the tilt", let the offset slide over the course of a ride. It was built in September, put through five adversarial reviews (each found it accepting contradictory evidence and reporting the contradiction as agreement), and removed on 23 September 2026.

What is left is about 3.5 m of spread in absolute height, mostly within single rides. It barely touches the colours, because slope is computed over 75 m windows where the drift is tiny: measured against high-resolution 1-metre terrain data, slope typically agrees to within about 0.8 percentage points. Absolute heights are good to a few metres, not to one.

Which rides count

Decided from the data, not from a list

A rebuild (Part 2, Step 5) replays stored rides, and so do the measuring tools in Part 6. Both skip rides that cannot be trusted, using two tests read from the rides themselves:

  • Scale. A ride whose heights dip below 1,000 m was recorded before heights were absolute; Colorado Springs is at about 1,800 m. Rides 5 and 6 are like this permanently, and their raw data cannot be converted.
  • Spikes. A ride where more than 15% of the steps between fixes imply an impossible grade is not a ride with spikes in it; it is spikes. Only ride 45 fails, at 20.7%; the next worst is 6.6%. Rides that record which sensor each height came from are exempt from this test.

49 of the 52 stored rides pass (through ride 89). These tests apply only to rebuilds and measurements: a ride saved from the phone is merged as it arrives. So a bad ride merged from the phone stays in the map until the next rebuild, which leaves it out.

    Across the 48 rides measured on 11 October, 26 genuinely ridden passes (1.24 km) show on the opposite direction's line instead of their own, and the gate rejects 4 (179 m). Small against 260 km of drawn riding, and every lever that was tried on them is in the table above.

For feature design · gaps a feature could fill

The red band is open-ended (cheap). There is no rider identity (expensive: accounts). The barometer works only on Android. Nothing is live during a ride. The map shows slope but not how sure it is: a line built from one pass looks the same as one built from five, although the database knows the count for every bucket.

How a change is measured

Before anything that touches the model ships

Every change to how rides are read is measured first, by replaying every usable ride through the real server code twice, once as shipped and once with the change, and comparing what would be drawn. The tools live in backend/ and are read-only: they never write to the database.

The witness

An independent judge of what the rider actually rode, built separately from the matcher so the matcher is not marking its own homework. For every street the matcher touched during a ride, it drops the ride's raw fixes onto that street and counts a pass wherever they cover at least 25 m in one direction, using nothing but the positions and the clock. When a change below the gate is being measured, it counts down to 15 m instead, because a witness cannot speak about anything shorter than its own floor. It never looks at streets the matcher did not touch, which is why the first open problem above is still open.

Comparing the witness with the map gives every pass the map missed a cause; "What a lost pass looks like", earlier in this part, translates each into what shows on the map.

Part 7

Reference

The whole thing in one pass

Every stage, and what one item of data has become by the time it gets there

What makes this system hard to hold in your head is that the unit of data takes four forms. It starts as a fix. Fixes become runs. Runs become buckets. Buckets become coloured pieces. Each stage judges the unit it was handed, not the one before it, which is why "a fix is matched to a bucket" skips the steps that do most of the work.

What "merge" writes, in plain terms

The last box on the server does three separate writes for every run that survived:

  • Blend into the running means. Each of the run's bucket heights is averaged into whatever is already stored at that street, direction and 15 m mark, weighted by how many passes are already there. This is the elevation model itself (segment_elevation_buckets).
  • Widen coverage. A second table (segment_coverage) holds one row per street and direction recording the stretch ever ridden, as a start metre and an end metre. This run's reach is merged into that range. It is what tells the drawing code where to stop.
  • Write a receipt. A third table (session_segment_matches) gets one row saying, for example, "ride 43 contributed a forward run on segment 12555, from fix 8811 to fix 8847". It stores no heights and no shapes, and drawing the map never reads it. It exists so questions about where data came from can be answered later: how many streets a ride contributed to, which rides contributed nothing, and that a ride can no longer be deleted.
Smoothing and anchoring are not the same thing

Both touch heights, so they are easy to confuse, but they are different boxes doing opposite jobs.

Smoothing is the second box. It looks only at this ride's own heights, in time order, forwards and then backwards, and takes the jitter off without moving the ride's overall level or delaying its hills.

Anchoring is the eighth box, and the one that consults the terrain survey. It leaves the ride's shape alone and slides the whole ride up or down by one number, so a ride that started from a bad GPS height lands on the same vertical scale as every other. One removes wobble within a ride; the other fixes where the whole ride sits.

How many buckets does a segment get?

Bucket positions are fixed multiples of 15 m from where travel enters the segment: 0, 15, 30, 45 and so on. A 104-metre block therefore has eight possible positions, 0 through 105, decided entirely by its length. Nothing about a ride changes where they are.

What a ride decides is which positions exist as rows. A bucket row is created the first time a run that passed the gate lands on it, so a street ridden only halfway has rows for half its positions. And because buckets are identified by (segment, direction, distance), a two-way street keeps two independent sets.

Where the judgement calls are, and where they are not

Every one of them lives in the save path, and every one decides what data is allowed into the model, never how it is displayed. The filters decide which fixes are real; matching decides which street a fix belongs to; rejoining decides whether two runs were really one; the gate decides whether a run counts as riding the street; drawing to the junction decides how far a line reaches; the anchor decides how far to shift the ride.

Colouring has none. Given a set of buckets, the slope of every gap and the colour it maps to are fully determined. Its two tuning numbers, the six-bucket window and the ±25% cap, smooth and bound the arithmetic, but they do not choose between competing readings of the ride the way the judgement calls do.

B · Recording a ride

  1. Press Start: nothing goes over the network

    Permissions, the barometer module started, Android's location tracking started. A ride begins with no server record at all, because requiring one meant a weak signal at the trailhead blocked the ride entirely.

  2. Fixes accumulate on the phone

    Written to phone storage, not app memory. The trail drawn on screen during the ride is a separate 2-second read of that storage, and the screen is kept awake while recording (on Android only so the map stays visible on a handlebar mount).

  3. Sampling follows speed

    The app asks for a fix every 11 m, because a fixed timer samples descents, the fastest part of a ride, least. Turns switch GPS to high accuracy for a few seconds. Android delivers fixes every 1 to 2 seconds in practice (Step 2).

  4. Press Stop: is this a real ride?

    Judged by how far the ride ever got from its starting point. No fixes: discarded silently. Under 75 m: the app asks, offering "Save anyway". Not total distance travelled, because GPS noise does not cancel when it is added up: a phone lying on a table manufactures hundreds of metres of "distance", while its distance from the start stays inside the accuracy circle however long it lies there.

  5. Create the record, upload, end

    Ask for a ride number and save it immediately, upload the fixes 125 at a time (dropping each piece from the phone's list as the server acknowledges it), then send /end. Only then is the phone's copy cleared. A ride stranded on the phone by a crash is recovered on the next launch.

C · Saving a ride, on the server

All of this happens inside one transaction: it either all lands or none of it does, and a failed save can simply be retried.

  1. Guards

    Already ended? Answer "already processed" and do nothing. No fixes at all? Delete the record.

  2. Load

    The ride's fixes in time order, plus every canonical segment within about 500 m of them.

  3. Drop impossible fixes

    Impossible speed first, then impossible height.

  4. Smooth

    Forwards then backwards over the ride's own heights.

  5. Match

    Each fix gains a street and a direction. Consecutive fixes that agree on both become a run, and from here on nothing judges single fixes.

  6. Rejoin

    Runs on one street and direction under 45 s apart become one.

  7. Measure and gate each run

    Drop each fix onto the street, round its distance along to the nearest 15 m mark, and average the heights that share a mark. Measure the span, bracketing fixes included. Keep the run only if it spans 25 m or 70% of the block.

  8. Draw to the junction

    Stretch the run's coverage to any end the rider provably rode through.

  9. Anchor

    One offset for the whole ride, from terrain heights. This is why nothing is written until every run has been measured.

  10. Merge

    Three writes per surviving run: blend the buckets, widen coverage, write the receipt.

    Irreversible, because the blend is a running mean: once a ride's numbers are averaged in, no subtraction takes them out. Undoing a bad ride means a rebuild, which wipes the model and replays every usable ride from its raw fixes.

D · Drawing the map

  1. The phone decides whether to ask

    It asks for a box 20% wider than the screen, so small pans stay inside what is loaded. If the last request already covered the screen, no request is made.

  2. The server finds what has data

    Canonical segments in the box with at least one bucket. Segments with no data are skipped: the network covers a whole city.

  3. The server builds the lines

    Clip each line to its coverage, offset it to its side, compute a slope per gap, and send "colour stops": for each gap, where its piece starts along the line and which colour it takes.

  4. The phone cuts them into pieces

    Between each pair of neighbouring stops the colour is constant, so the phone draws one short line in that colour: six pieces for South Wahsatch, even though all six are green. The map library can colour a whole line one way but cannot colour one line with changing colours along it, so many short solid pieces stand in for one graded line.

  5. Merge, never replace

    New answers are merged into what is already drawn, and a counter throws away any answer that arrives after a newer one. Both exist because lines visibly flickered during rides.
