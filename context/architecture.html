Part 1

Foundations

The idea

Why this app exists

Every cycling map tells you a hill exists. None tell you which way it hurts.

A street that is a pleasant coast heading south is a grind heading north. Existing maps collapse that into one number. This app keeps them separate: it stores a different elevation profile for each direction of travel, and draws two colored lines per street, one for each way.

The second idea: riding a street again makes the data better, not just newer. Every stored height is an average across every pass ever made over that spot. The fourth ride down your street nudges the number toward the truth rather than replacing it.

That's it. Everything else in this document is machinery in service of those two ideas.

Databases in five minutes

Everything you need to follow the rest

A database is a set of tables. A table is a grid, like a spreadsheet tab. It has named columns down the side and one row per thing it stores.

Our segments table has one row per block of street. Its columns include street_name, length_m, geom. Here are three real rows out of about 31,000:

idstreet_namelength_mbearing_degcanonical_segment_id
12555South Wahsatch Avenue104.4182null
12556South Wahsatch Avenue104.4182null
20871null96.218112555
null

null means "there is no value here" — the box is empty. It is different from zero and different from an empty word. Zero is a number; null is the absence of one.

In the table above, row 20871 has street_name = null: that sidewalk has no name in OpenStreetMap. Rows 12555 and 12556 have canonical_segment_id = null: they are main routes in their own right, not sidewalks pointing at something else. Row 20871's canonical_segment_id = 12555 means "I am the sidewalk running alongside segment 12555."

So when I wrote "only rows where that column is null are matched or drawn," it means: ignore anything that is a sidewalk pointing at a road; only consider the roads themselves.

Row, and why it matters here

A row is one entry. When I say "ten rides leave one row, not ten," I mean: the database does not store ten separate measurements of that spot. It stores one entry holding the average of all ten, plus a count of how many went into it.

Folded in

My phrase, and a bad one. "Folding a ride in" means merging its measurements into the stored averages. Concretely, for each spot the ride passed:

new average = (old average × old count + new reading) ÷ (old count + 1)

Once that runs, the old average is gone — overwritten by the new one. You cannot recover the individual reading afterwards, which is why a ride cannot be "un-folded."

Part 2

One block, end to end

The block itself

Real data · segment 12555

Everything from here to the end of Part 2 follows one real block that you have ridden four times: South Wahsatch Avenue, database id 12555. It runs almost due south, is 104.4 metres long, and it is a genuinely good example because it renders a different colour in each direction.

Step 1 — The segment

The unit the whole system is built on

Segment

One block of one street. Not the whole street — just the piece between two intersections. South Wahsatch Avenue runs for over a kilometre and is stored as roughly a dozen segments, one per block.

OpenStreetMap gives us a "way" that might run the whole length of the street. The pipeline cuts it wherever it touches another street we kept. Each resulting piece becomes one row.

Each segment row stores three things that need explaining:

geom — a LineString

An ordered list of GPS coordinates, joined by straight lines. That is all a LineString is. Segment 12555's is four points long:

[-104.81843, 38.82638] → [-104.81845, 38.82591] → [-104.81846, 38.82578] → [-104.81847, 38.82544]

Four points, three straight hops between them. That is enough because this block is basically straight; a curved street would need more points to trace the curve.

length_m

How long the block is, in metres, measured along that line. Here: 104.4.

bearing_deg

A compass heading, 0–360°, for the straight line from the first point to the last. 0 is north, 90 east, 180 south, 270 west.

Segment 12555's bearing is 182° — almost exactly south. It is not random; it is measured. It is stored because comparing your heading to the street's heading is how the server decides which way you were going.

Why you sometimes see two colours before reaching an intersection

You asked this directly, and it is the single most important thing in this document. The colored pieces on your map are not segments and are not the thing that gets cut at intersections. A single 104-metre segment normally gets painted as six separate colored pieces. Part 3 explains this properly — it deserves its own section.

Step 2 — GPS fixes

What the phone actually records

GPS fix

Yes — exactly what you guessed. One fix is one ping: a single moment where the phone reports where it thinks it is. Our app asks for a fix roughly every 1–4 seconds, adjusted so they land about 11 metres apart no matter how fast you are going.

Each fix carries seven values:

FieldMeaningExample
recordedAtWhen2026-08-18T19:42:11Z
lat, lonWhere38.82612, -104.81844
elevationMHeight above sea level1825.4
headingDegWhich way you were pointing184
speedMpsHow fast, metres per second5.2
accuracyMHow much the phone trusts itself8

Height comes from the barometer where possible — it measures air pressure, and air pressure changes as you climb. It's far more sensitive than GPS altitude. Its problem is that it only measures change; where you started is unknown to it. That's what the DEM anchor in Part 5 fixes.

Riding this block southbound at about 5 m/s produces roughly nine fixes. They are buffered on the phone and uploaded when you press Stop.

Step 3 — The run

Grouping fixes by street

Run

The group of consecutive fixes that all landed on the same segment, going the same way.

Ride five blocks down South Wahsatch and you produce five runs — one per block. Turn around and ride back and you produce five more, this time marked backward.

Direction: forward and backward

Not north/south. Forward means travelling from the segment's first stored point toward its last. Backward is the other way.

For segment 12555 the first point is at the north end, so forward = southbound and backward = northbound. For the next street over it might be the reverse — it depends purely on which way the OpenStreetMap contributor happened to draw it.

And yes, start_node_id is exactly what you thought: the identifier of the point where the block begins.

Step 4 — Buckets

The part that didn't land last time

Here is the problem buckets solve. You ride this block in August and again in November. Your fixes land in completely different spots both times — GPS never repeats exactly. So how do you average two measurements that were never taken at the same place?

You round them to shared positions, the same way you'd round prices to the nearest dollar so you can compare them.

Bucket

A marked position every 15 metres along a block, holding one height value.

Segment 12555 is 104.4 m long, so it has buckets at 15, 30, 45, 60, 75, 90 and 105 metres from its start — seven of them. Every fix gets assigned to whichever bucket it is nearest, and its height is averaged in there.

A bucket is invisible. It is not drawn on the map. It is a storage slot.

Where a bucket sits on the real map

On the ground, bucket "45" for this segment is a specific spot: 45 metres south of the north-end intersection, on the centreline. If you stood there with a tape measure you could find it. It has no width on the map and nothing is drawn at it — it is a filing position, like a shelf label.

Is it one grid laid over the whole map?

No. There is no city-wide grid, and nothing is measured from a common origin. The 15 m spacing is one-dimensional and it belongs to a single segment: each segment carries its own ruler that starts at zero at its own end and counts along its own centreline. Two segments meeting at an intersection each have their own zero, a few metres apart, pointing different ways.

So bucket 30 on South Wahsatch and bucket 30 on East Fountain are not related, not aligned, and not near each other. The number is only meaningful once you say which segment — which is why a bucket row is keyed by (segment, direction, distance) and never by distance alone.

Step 5 — The running mean

How four rides become one number

Look at the "4 rides" bucket at 30 m in the diagram above. Its stored value is 1824.98. That single number is the average of four separate passes.

Here is how it got there, one ride at a time:

RideReadingStored afterCountArithmetic
1st1825.401825.401first one, stored as-is
2nd1824.601825.002(1825.40×1 + 1824.60) ÷ 2
3rd1824.901824.973(1825.00×2 + 1824.90) ÷ 3
4th1825.011824.984(1824.97×3 + 1825.01) ÷ 4

Note what is not stored: the four individual readings. Only the running total's average and the count survive. That is why a ride cannot be removed from the model — you would need the original reading to reverse the arithmetic, and it is gone.

But nothing is actually locked

You asked: if a running mean can't be edited, how do you ever change anything? The answer is that the raw GPS fixes are never deleted. Every sample from every ride is still sitting in session_samples. The bucket averages are only a summary computed from them.

So changing the bucket size from 15 m to 20 m, or changing how slope is measured, is entirely possible. You change the code and run npm run rebuild-model, which throws away every summary and recomputes it from the original fixes. Nothing is lost. It just can't be nudged in place — it has to be rebuilt whole.

Step 6 — Coverage

Where the paint starts and stops

Buckets tell you how high the road is at seven positions. They do not tell you how much of the block you actually rode — and those are genuinely different questions.

Coverage

Two numbers per direction: where your riding started on this block, and where it ended. For segment 12555 southbound, coverage is 8.9 m → 104.4 m.

It exists so the map knows where to start and stop painting. Buckets can't answer that, because they sit on a fixed 15 m grid: the first bucket is at 15 m even if you actually entered the block at 8.9 m.

That 6-metre difference was a visible bug. Painting from the first bucket left a small unpainted stub at the head of nearly every line, and the map looked like a dashed route rather than a continuous one. Recording where the riding really started fixed it.

Coverage also widens over time. Ride the first half of a block one day and the second half another, and the two ranges are combined into one — between them, you covered the whole thing.

Step 7 — Drawing it

Where the two colours come from

Now the payoff. Same block, same asphalt, two directions, two different answers.

Both directions independently agree the north end is higher. Ridden south you're descending; ridden north you're climbing. That is the entire thesis of the app, visible in one block of real data.

That opposite-running ruler is the "one geometry row serving two independent profiles" sentence that didn't make sense before. There is one shape stored in the database. Two separate sets of height readings hang off it, measured from opposite ends, and drawn on opposite sides.

Part 3

The big misconception

Colored pieces are not buckets

Read this one twice

Your notes said: "I thought each colored segment was essentially a bucket." They are three different things, and keeping them apart makes everything else click.

SegmentBucketColored piece
What it isOne block of streetA height reading at a positionA stretch of one colour on screen
Size8–150 mNo size — a pointUsually 15 m, but varies
Visible?NoNoYes — this is what you see
How many on 1255517 per direction6 per direction
Cut at intersections?YesNoNo

How the colour of each piece is decided

Not by comparing two neighbouring buckets — that turned out to be too noisy. A single slightly-off barometer reading could swing the result by a whole colour band, which is why a flat street once came out speckled purple and red.

Two words first: gap, and window

A gap is the stretch of street between two neighbouring buckets. Buckets sit every 15 m, so a block with buckets at 15, 30, 45, 60, 75, 90 and 105 has six gaps between them. A gap is a piece of ground, 15 m long — and it is exactly the piece that gets painted one solid colour. That is what a coloured piece is, and it is the same "six pieces from seven buckets" the picture just above was making.

Every gap gets its own colour. Nothing is left out; the whole ridden stretch of street is covered by gaps laid end to end. So when I say "colouring the gap from 45 m to 60 m", that is one turn of a loop that runs over all six. It has to be described one gap at a time only because each one is decided independently of the others.

A window is the set of buckets consulted to decide one gap's colour. It is not a piece of ground and nothing is ever drawn at its width — it is purely "which stored heights do I read in order to work out how steep this 15 m piece is". The window is deliberately wider than the gap it decides, and the rest of this section is about why.

What a best-fit line is

Picture the buckets on a chart: their positions along the bottom, their stored heights up the side. Six dots. There are infinitely many straight lines you could draw across them, and none of them will pass through all six — the heights are measurements, and measurements wobble.

A best-fit line is the single line that comes closest to all six at once. "Closest" needs a definition, and the usual one is called least squares: for each dot, measure the vertical distance from the dot up or down to the line — call that the miss — square it, and add up all six. The best-fit line is the one where that total comes out smallest. Hence the name: least total of the squares.

Squaring does two jobs. It stops a miss above the line from cancelling out a miss below it, and it makes one large miss cost far more than several small ones — so the line gets pulled toward the crowd rather than toward any single odd reading. The slope of that line is the number we colour by.

Why six dots instead of two

Which six, exactly

The window reaches two buckets beyond each end of its gap. For the gap from 45 m to 60 m that means buckets 45 and 60 themselves, plus 15 and 30 before, plus 75 and 90 after — six buckets covering 75 metres of street, used to colour 15 metres of it. Move to the next gap and the window slides along with it, so neighbouring gaps share most of their buckets. That overlap is why colours change gradually along a street instead of jumping.

Finally the result is capped at ±25%, since no rideable street here is steeper than that — past that it is a bad reading, not terrain.

≤ −8%plunge
−8 to −3descent
−3 to 0easy down
0 to +3easy up
+3 to +6climb
> +6%wall

What these percentages actually feel like

First, clearing up a trap in the numbers you have been reading. Heights like 1824 m and 1826 m are altitude above sea level, not climb. Colorado Springs sits at roughly 1,800 m, which is about 5,900 ft, so every height in this database starts near that. A change from 1824 to 1826 is a 2-metre rise — and on its own that tells you nothing about steepness.

Slope is rise divided by distance travelled forward. That same 2 m rise is a 13% wall if you gained it over 15 m of street, and a gentle 2% if you gained it over 100 m. The percentage is the only thing that describes steepness; the raw heights never do.

The percentage is also unit-free, which is handy if you think in feet: 6% means 6 metres up per 100 metres forward and 6 feet up per 100 feet forward. The same number works in both. Some reference points:

GradeSomething you know at that grade
2 – 3%Barely perceptible; you notice it in your speed, not your legs
6%The steepest a US highway normally goes before runaway-truck ramps appear
8.3%The legal maximum for a wheelchair ramp
7 – 9%The average grade of a famous Alpine cycling pass, sustained for an hour
15 – 25%Mountain-bike trail pitches; walking territory for most riders

So yes — sustained 6% is a real climb on a bicycle, and painting it red is defensible. But note the weakness this reveals: the red band is open-ended. Everything above 6% is the same red, so a 7% street and a 20% trail pitch are drawn identically, right up to the ±25% clamp. That was a fine simplification for a city grid where almost nothing exceeds 8%. On mountain trails it throws away most of the interesting range, and splitting red into two or three bands is probably the single cheapest improvement available — it needs no rebuild, since colours are computed fresh on every request.

So how do I change anything?

Answering your question directly

You asked what happens if a segment needs to change size or be elongated. Here is the honest answer for each kind of change.

You want to changeWhat to doCost
Bucket size (15 m → something else) Edit the constant, then npm run rebuild-model A minute. Nothing lost.
Colour thresholds, slope window Edit and redeploy. No rebuild needed — these are applied when drawing. Seconds.
Which streets exist, or where a block ends Re-run the OSM pipeline, then rebuild-model Longer. Old segment ids may change.
Remove one bad ride from the model Delete its samples, then rebuild-model Rebuild is the only way — you cannot subtract it.
Elongate one segment by hand Not supported, and shouldn't be — segments come from OpenStreetMap, so fix it upstream in OSM or in the pipeline's splitting rules. —

The mental model to hold: raw GPS samples are the truth; everything else is a cache. Any derived thing can be thrown away and recomputed. That is why the rebuild script exists and why it runs the exact same code as the live upload path — if they ever drifted apart, a rebuild would produce a model the app could never reproduce.

Part 4

The three programs

Who does what

Now that the vocabulary exists

First: a genuine name collision

You spotted that the old diagram showed /segments inside the server box, when the pipeline is what makes segments. Both are correct, because the same word means two things:

segments — a table in the database. Where street shapes are stored. Written by the pipeline.

/segments — a URL on the server. An address the phone sends a request to, meaning "give me the colored lines for this part of the map." It reads from that table, but it is not the table.

The leading slash is the tell: anything starting with / in these diagrams is a web address, not storage.

"Runs by hand on your laptop"

The pipeline is not a server and nothing starts it automatically. It is four small programs sitting in the osm-pipeline/ folder. You open a terminal, type npm run fetch, and it does its job and exits — like running a spreadsheet macro, not like a website.

All four are manual. You run them when you need to — which happens rarely, only when the map area grows or the splitting rules change. Nothing runs them for you. Each one reads its input, does its work, and stops.

The split that actually matters

Front end versus back end here is not "screen versus server." It is measurement versus interpretation.

The phone is a sensor with a screen. It records what it observed, keeps it safe, and draws whatever it is handed. It holds no opinion about what a street is — it does no geography maths at all.

Every judgement lives on the server: which street you were on, which way you faced, whether you really rode it, how steep it is. Those need the whole street network and the history of every previous ride, and neither of those fits on a phone.

Part 5

The judgement calls

What a heuristic is

A word I used without defining

Heuristic

A rule of thumb that is usually right, used where being certain is impossible.

"If a fix is within 25 metres of a street and pointing along it, assume the rider was on that street" is a heuristic. It is not a proof. Sometimes it is wrong. It is used because there is no way to know which street you were on — GPS is fuzzy, streets run parallel, and the phone can't see.

Every heuristic in this project has a threshold number attached, and every one of those numbers was tuned by looking at real rides and seeing what worked.

The three that matter are below.

The traversal gate

Heuristic 1 · "did you actually ride this, or just touch it?"

The problem, concretely

You ride east along East Fountain Boulevard. You cross South Institute Street. For one or two seconds you are physically in that intersection — so a GPS fix lands there, and it is genuinely within a few metres of South Institute Street.

The server sees a fix on South Institute Street and a height reading, and paints a 139-metre gradient line down a street you never rode. Five such phantom lines were visible on your map.

The fix, built up slowly

The test is: did this run cover any ground along that street? To answer that we need one more term.

Distance along

A GPS fix is a point somewhere near the street — never exactly on the stored centreline, because the centreline is a drawn line and the fix is a noisy measurement. Distance along throws away how far to the side the fix landed and keeps a single number: how far down the segment it sits, measured from the segment's start.

Every segment has a start — the first node OSM stored for that block. On South Wahsatch Avenue, which runs north to south, that start is the north end. A fix that lands 40 metres down the block has a distance along of 40 m whether the fix itself was 2 metres off the centreline or 12.

Sideways distance is not useless — it just belongs to an earlier step. The matcher computes it to decide which street a fix belongs to, and once that decision is made it plays no further part. Only distance along and height go into the elevation model.

But "discarded" is too strong, and the difference matters. The computed sideways distance is never written down anywhere. The raw fix it was computed from — its latitude and longitude — is kept forever in session_samples. So the number is not preserved, but it is always recoverable, and a rebuild does exactly that: it re-reads the raw positions and recomputes every sideways distance from scratch. That is the whole reason a matching decision made last year can be revisited after a constant changes.

Span

Within one run: the largest distance along, minus the smallest. Take the ruler from the picture above, mark every fix belonging to that run on it, and measure from the leftmost mark to the rightmost. That width is the span.

It is built out of fixes, so it inherits their spacing. If a run's first fix landed 9 m into the block and its last landed 90 m in, the span from the run's own fixes is 81 m, not the block's full 104 m — the first nine metres and the last fourteen were never sampled. In practice the two bracketing fixes usually close that gap: on a genuine pass-through they sit outside the block entirely and clamp to its ends, taking the span to the full 104 m.

Span belongs to one run, not to the segment. The gate judges runs, one at a time, and a segment collects many runs over many rides. The segment does enter, but only as the second test's denominator: the coverage fraction is this run's span divided by the whole segment's length, so 81 m on a 104 m block is 78%. A segment's total ridden extent across every ride is tracked separately in segment_coverage; that is what the renderer clips lines to, and it plays no part in the gate.

It is not the distance you travelled, and it is not how many fixes there were. A run of eighty fixes that never moved has a span of nothing. The three rows below are the same 104 m block, drawn to the same scale.

So the rule becomes: keep the run only if span is at least 25 metres, or it covers at least 70% of the block. Two tests because neither works alone — a plain 25 m rule throws away genuinely-ridden short connector pieces, and a plain percentage rule lets a touch on a very short segment through.

Two unrelated rules, both the number 25

This trips people up, and the two are easy to conflate because they share a value by pure coincidence. They measure different axes, judge different things, and live in different files.

MAX_MATCH_DISTANCE_MMIN_SPAN_M

Changing one has nothing to do with the other. There is a third 25 in the codebase — MAX_PLAUSIBLE_SLOPE_PCT — but that one is a percentage, in the drawing code, and is not easily mistaken for either.

Why one fix has a span of zero

Span is a difference between two things: the furthest and the nearest. If a run contains only one fix, then the furthest and the nearest are the same fix, so the difference is zero. 40 − 40 = 0.

That broke real crossings. Fixes land about 11 m apart, so riding across a 10-metre stub of trail might produce exactly one fix on it. One fix, span zero, rejected. Twenty three legitimate lines disappeared this way in a single ride, showing up as gaps.

Bracketing fix

The fix immediately before a run starts, and the one immediately after it ends. These are the "bookends" around it.

Yes — these are fixes from outside the run. The server holds the whole ride as one list of fixes in time order. A run is a stretch of that list. The bracketing fixes are simply the list entry immediately before the stretch and the one immediately after it.

What those two fixes were doing does not matter. One may belong to a different run on a different street; one may have matched nothing at all; one may have been skipped for bad accuracy or a missing compass reading. They are neighbours in time, not members of anything.

How they are used: each is projected onto this segment — the same sideways drop as any other fix, clamped to the segment's ends if it falls past them — and the two landing points are allowed to stretch the span. Their heights are never read. They widen the measurement on the ruler without contributing a single elevation reading to the model, which is correct: they were recorded somewhere else.

This fixes two problems. Short crossings: A 10-metre trail stub produces one or zero fixes on it. The bookends sit on either side of the stub. One bookend's perpendicular lands at 0 m, the other's at 10 m. Span = 10 m. Kept. Phantom lines: When you ride past a cross street, the bookends are on the main street you're riding, but if you drop a perpendicular onto the cross street, both land at nearly the same distance-along point. Span ≈ 0. Rejected. The bookends don't resurrect phantoms, because they're on the wrong segment the whole time.

Picking the right street

Heuristic 2 · map matching

For each fix, the server asks: which street was this on, and which way was I going? Four rules, in order.

  1. Throw out untrustworthy fixes

    No heading recorded: the phone's compass sometimes fails. Skip this fix entirely.
    Accuracy worse than 30 m: the phone says "I think I'm here, but I could be off by 30 metres." That's inside the spacing between parallel streets. One bad fix can't tell a street from its sidewalk.

  2. Find nearby candidates

    Check every segment in the database. If its centreline comes within 25 metres of this GPS fix, it's a candidate. This is purely a distance filter — you could be on this street, or you could be on another one nearby.

  3. Check you were pointing the right way

    Your heading is the direction your phone thought you were facing. The segment's bearing is a single compass direction for the whole piece, measured from its first point to its last. If the two match within 45°, you were riding forward down it. If they're 180° apart (opposite), you were riding backward. If neither, you were crossing it (perpendicular), so drop this candidate.

  4. Prefer to stay where you already are

    The problem: a street and its sidewalk sit 5–10 metres apart. With GPS error this big, every fix has multiple candidates. Picking the closest one for every fix independently made a single ride flip back and forth between the street and its sidewalk, scattering one pass across several parallel lines.
    The fix: if you're already on a run (riding a particular segment), a rival segment has to be more than 8 metres closer to steal you. Only a genuine turn onto a different street wins. Staying put costs less than switching, so hysteresis keeps you on the line you're on.

Honest limitation

This is prototype-grade: nearest street, plus a bearing check, plus a reluctance to switch. It is not a real map-matching algorithm, and it can still misfire at complex intersections. It is good enough to keep one ride on one line. If that stops holding, the answer is a proper map-matcher rather than more thresholds.

Fragment stitching on mountain trails

Heuristic 2b · mountain-specific, merged with the gate

The problem: switchbacks break runs into pieces

On a street grid, the heuristic works fine — your heading stays within 45° of a street's bearing the whole way. On a switchback trail with tight turns, it breaks down.

You climb a trail northbound. Hairpin. You climb southbound. To the database, the trail is stored as one straight arrow pointing east (net direction across the hillside). But your heading was north, then south — both 90° away from east. Both failed the 45° test. One continuous 146-metre descent arrived as five separate runs, each 1–15 metres.

The traversal gate then looked at each piece individually. A 9-metre span on a 146-metre trail: rejected. Repeat five times. The entire descent disappeared from the map.

Two different things called a "line"

I have been saying "the stored line" without explaining it, and it matters here, because the answer is the opposite of what you would guess. The stored line exists before you ride anywhere.

The stored line — segment geometry

A list of latitude/longitude points forming a polyline, downloaded from OpenStreetMap by npm run fetch and sitting in the geom column of the segments table. It exists for every street and trail in the city whether or not anyone has ever ridden there.

You have already met it: this is the dashed centreline from Step 1, where the point was that the database stores no road width and no edges — only this line, its length, and which way it points.

It is never compared as text. It is used geometrically: how far is this fix from that polyline, and where along it does the fix land. Both of those are the operations from the traversal-gate section — sideways distance, and distance along.

Each segment also carries one bearing_deg: the compass direction of a straight line drawn from the polyline's first point to its last. It is computed once at import and never changes. That single number is what the 45° heading test compares your heading against — and on a switchback it is the number that is lying, because a zigzag's start-to-end direction says nothing about the direction you are facing at any moment on it.

The gradient line — what gets drawn

The coloured thing on the map. This one is built from your fixes: buckets, slopes, colour bands. It is drawn on top of the stored line, offset 4 m to one side so both directions are visible at once.

The fix: rejoin fragments within a time window

Two fragments of the same descent are separated in time by the length of time you spent matching nowhere. Measured across every ride recorded so far:

  • Same traversal: fragments are 0–45 seconds apart (49 of 51 cases)
  • Separate crossings of the same trail: at least 90 seconds apart, never in between

What stitchFragmentedRuns actually does

Considerably less than the name suggests, and that is worth being precise about. It walks the runs in time order, keeping a note of the most recent run seen for each (segment, direction) pair. When a new run turns up on a pair it has seen before, it checks exactly one thing: how many seconds passed between the previous run's last fix and this run's first fix. Under 45, it appends this run's fixes onto the end of the previous run and throws away the separate run. Over 45, it starts a fresh one.

Because appending moves the previous run's end time forward, the next fragment is measured against the new end. That is what lets five fragments chain into one run rather than merely joining in pairs.

Three things it does not do

It does not change any bearing. The segment's stored bearing is import-time data from OpenStreetMap and is never written to by anything in the app. Nothing "makes the bearing match the trail".

It does not re-decide any fix's direction. Every fragment already had "forward" or "backward" stamped on it at match time, and stitching only ever joins fragments that already agree on segment and direction. Two fragments pointing opposite ways stay separate no matter how close in time.

It does not rescue the fixes that failed to match. Everything recorded on the long legs — the great majority of the descent — failed the heading test, stayed unmatched, and contributes no height to anything. Those readings are simply gone.

So what does it actually recover?

Extent, not data. Remember what the gate measures: span, the largest distance along in the run minus the smallest. Five separate runs meant five separate spans of 1–15 m, each judged alone and each failing the 25 m minimum. Joined into one run, the first fix sits near the top of the descent and the last near the bottom, so the span is the full 146 m and the gate keeps it.

The heights that end up in the buckets are exactly the same heights as before, from exactly the same five fragments. Not one extra reading was recovered. The only thing that changed is that the gate now measures across all five at once instead of judging each in isolation — which is also why stitching has to run before the gate rather than after it.

Streets were never touched. Genuine intersection touches stayed dead (94 → 92 clips kept). Fragments dropped from 75 → 2. The 92-clip number is the crucial one: it proves no phantom lines were re-created by loosening the rule for trails. The two remaining fragments are individual corner clips, correctly rejected because they are not traversals.

The DEM anchor

Heuristic 3 · rewritten from scratch

The problem, in one analogy

Imagine measuring the height of a staircase with a very precise ruler that has no zero mark. You can say with confidence "each step is 18 centimetres taller than the last." You cannot say how high the bottom step is above the ground.

That is a phone barometer. It measures changes in height beautifully, because air pressure drops as you climb. But it has no idea what absolute height it started at — that depends on the weather.

So each ride guesses its starting height from the GPS altitude of its very first fix. That single reading carries 10–20 m of error. The whole ride is then measured relative to that guess, so the whole ride is wrong by the same amount.

Why that breaks the map

A constant error would be harmless if every ride made the same one. They don't. Four of your rides were off by −13.20, −13.35, −14.85 and −16.54 metres — a spread of 3.3 m.

Now average those together in the buckets. Where a ride that thought it was low meets a ride that thought it was high, the running mean welds two profiles that disagree by metres, and an invented step appears in the road exactly at the seam.

DEM — Digital Elevation Model

A published dataset of how high the ground is, everywhere. Ours comes from the US Geological Survey, sampled at 10-metre spacing across the whole country.

It has the opposite strengths from a barometer: rock-solid absolute heights that never drift, but coarser detail — it doesn't know about a small dip in one block.

The fix: use each source for what it's good at

Take the barometer's shape — the hill it traced out, perfect except for a constant offset — and the DEM's level — the official "this is how high the ground really is" number. Concretely, after measuring a ride but before storing any of it:

  1. Look up the terrain. For every GPS coordinate the ride touched, ask the DEM "how high is the ground here?"
  2. Measure the gap. For each spot, subtract the official height from what the ride thought it was. This gives you a list of offsets.
  3. Find the middle offset. Line those differences up in order of size — smallest to largest, ignoring where along the ride each one came from — and take the one sitting in the middle of the list. That is the median, and it becomes the single offset for the whole ride.
  4. Shift everything. Subtract that one median offset from every single height in the ride. Now store it.

Concrete example. A ride measures five spots as 1814, 1846, 1815, 1812 and 1816 m. The terrain says those same spots are 1800, 1801, 1801, 1800 and 1801 m. Subtracting one list from the other gives five differences — and one of them is clearly wrong:

as recorded, in ride order+14   +45   +14   +12   +15
sorted, smallest to largest+12   +14   +14   +15   +45
the middle one is the median+14

Every height in the ride then drops by 14 m. Notice what the +45 would have done to an average: it drags the mean up to +20, which would have shoved the entire ride 6 metres underground. Sorting and taking the middle gives that bad reading exactly the weight of any other single reading — one vote — no matter how absurd its value. That is the whole reason for choosing median over average here.

Four guards keep it honest:

  • One number per ride, never per street. If you tried to fit one offset for all rides on South Wahsatch Avenue southbound, you'd be assuming the road is flat. The fit would swallow the real 2.3-metre climb that genuinely exists, plus the barometer drift. Fitting per ride leaves the real shape alone.
  • The middle value, not the average. If one fix was taken inside a tunnel (a few metres off), or a bridge misreported height, one bad outlier would drag an average way off. The median ignores it entirely — it only cares about the middle value when all offsets are sorted.
  • Fewer than 10 overlapping points → don't bother. If the ride only touched 8 spots in the DEM database, you'd be fitting to noise. So short rides get no anchor and stay on their GPS altitude. Better an untrusted absolute height than a confident fit to nothing.
  • More than 60 m off → refuse. If the median offset is 60 metres or worse, something is very wrong: a GPS fix in a tunnel, a misaligned ride, or the ride happened somewhere the DEM doesn't cover. That's not drift, that's a broken ride. Hiding it with a wrong anchor is worse than leaving it broken.
Privacy — worth preserving

Only OpenStreetMap street coordinates are sent to the terrain service — public data about where roads are. Your ride traces never leave the server. Every looked-up point is cached forever, because terrain doesn't move.

A known imperfection, stated plainly

Look back at the two directions on segment 12555: southbound sits around 1824 m and northbound around 1822 m. That's the same asphalt, so they should match, and they don't — they're about 2 m apart.

The anchor is fitted per ride, and the two directions were ridden on different days, so a residual disagreement survives. It does not affect the colours, because slope is computed within each direction separately. But it does mean the absolute heights are not yet trustworthy to better than a couple of metres. Fixing it properly means normalising across directions, which is on the list and not done.

Part 6

Reference

The whole thing in one pass

Every stage, and what one item of data has become by the time it gets there

The thing that makes this system hard to hold in your head is that the unit of data changes four times. You start with a fix. Fixes become runs. Runs become buckets. Buckets become coloured pieces. Each stage judges the unit it was handed, not the one before it — which is why "a fix is matched to a bucket" skips the two steps that do most of the work.

What "merge" writes, in plain terms

That last box does three separate writes, and one of them — the audit row — is a term I have been using without ever defining. All three are laid out fully in flow C below; here is what each one is:

  • Blend into the running means. Each of this run's bucket heights is averaged into whatever is already stored at that (street, direction, 15 m mark), weighted by how many rides are already there. This is the elevation model itself.
  • Widen coverage. A second table holds one row per street and direction recording which stretch of it has ever been ridden, as a start metre and an end metre. This run's reach is merged into that range. It is what tells the renderer where to stop drawing.
  • Write an audit row. A third table, session_segment_matches, gets one row saying "session 43 contributed a forward run on segment 12555, covering fixes 8811 through 8847". That is the whole content of an audit row: a receipt naming which ride produced which run on which street. It stores no heights and no geometry, and it is never read when drawing the map. It exists so questions about provenance can be answered later — how many segments did this ride actually contribute to, which rides contributed nothing and can be pruned, and what to clear before a rebuild replays everything from raw fixes.
Smoothing and anchoring are not the same thing

Both touch heights, so they are easy to conflate, but they are different boxes doing opposite jobs and neither one is the other's ingredient.

Smoothing is the second box. It looks only at this ride's own barometer readings, in time order, and replaces each with a blend of itself and the running average before it. No terrain data, no other rides, nothing external. It takes the jitter off the line without meaningfully changing the ride's overall height.

Anchoring is the seventh box, and it is the one that consults the DEM — a public elevation dataset for the terrain. It leaves the shape of the ride completely alone and slides the whole thing up or down by one number, so that a ride recorded on a day when the barometer was reading 14 m high lands on the same vertical scale as every other ride.

One removes wobble within a ride. The other fixes where the whole ride sits. See the DEM anchor for how that offset is chosen.

How many buckets does a segment get?

Bucket positions are fixed multiples of 15 m from the segment's start: 0, 15, 30, 45, and so on. A 104-metre block therefore has eight possible slots — 0 through 105 — and that is decided entirely by the segment's length. Nothing about your ride changes where the slots are.

What your ride decides is which slots exist as rows. A bucket row is created the first time a qualifying run lands on it, so a street you have only ridden half of has rows for half its slots. And because buckets are keyed by (segment, direction, distance), a two-way street keeps two independent sets — riding it northbound never touches the southbound numbers.

Where the heuristics are, and where they are not

All three live in the save path, and all three decide what data is allowed into the model — never how it is displayed. Matching decides which street a fix belongs to; stitching decides whether two runs were really one; the gate decides whether a run counts as having ridden the street; the anchor decides how far to shift the ride vertically.

Colouring has none. Given a set of buckets, the slope of every gap and the colour it maps to are fully determined. The two tuning numbers there — the five-bucket window and the ±25% plausibility clamp — smooth and bound the arithmetic, but they do not choose between competing interpretations the way the three heuristics do.

Every trail lost to the geometric version was named, so the name test is what protects them.

B · Recording a ride

  1. Press Start — nothing goes over the network

    Permissions, barometer on, OS location task started. A ride begins with no server session at all, because requiring one meant a weak signal at the trailhead blocked the ride entirely.

  2. Fixes accumulate on the phone

    Written to phone storage, not app memory — Android can shut the app down and relaunch it mid-ride just to deliver a fix. The dotted line you see is a separate 2-second poll of that storage.

  3. Sampling rate follows your speed

    Aiming for a fix every 11 m. Descents are the fastest part of a ride, so a fixed timer samples them least — exactly backwards. Roughly power-neutral: slow climbs now get longer gaps, paying for the shorter ones downhill.

  4. Press Stop — is this a real ride?

    Measured by how far the ride ever got from its start point. Zero fixes → discard silently. Under 75 m → ask, offering "Save anyway".

    Not total distance travelled, because GPS noise doesn't cancel when you add it up — a phone on a table manufactures hundreds of metres of "distance". Distance from the start stays inside the accuracy circle however long you stand there.

  5. Get a session, upload, end

    Ask for a session id and save it immediately, upload fixes 250 at a time dropping each acknowledged chunk, then call /end. Only then is the phone's copy cleared.

C · Saving a ride, server side

All of this happens inside one transaction — it either all lands or none of it does.

  1. Guards

    Already ended? Return "already processed" and do nothing. No fixes at all? Delete the session.

  2. Load

    The ride's fixes in time order, plus every canonical segment in a box about 500 m around them.

  3. Smooth

    An exponential moving average over the ride's own heights, in time order: each reading is replaced by 30% of itself plus 70% of the average so far (EMA_ALPHA = 0.3, about the last three seconds). Nothing external is consulted — this is the ride steadying its own barometer, not a comparison against terrain data.

  4. Match — heuristic 2

    Each fix is given a street and a direction. Consecutive fixes that agree on both become a run. From here on nothing judges individual fixes; everything judges runs.

  5. Stitch — heuristic 2b

    Runs on the same street and direction less than 45 s apart are rejoined, so a switchback traversal is judged whole.

  6. Bucketize

    Project each of the run's fixes onto the street, round the distance along to the nearest 15 m mark, and average the heights that land on the same mark. Also record the run's reach — where along the street it started and ended, bracketing fixes included.

  7. Gate — heuristic 1

    Span at least 25 m, or at least 70% of the block. This happens after bucketizing, because the span it measures is a by-product of the projection. Failures are dropped here, before anything is written.

  8. Anchor — heuristic 3

    One offset for the whole ride, fitted against terrain data. This is why nothing can be written until every run has been measured.

  9. Merge

    Three writes per surviving run.

    Blend into the running means. Each bucket is averaged into whatever is already stored for that (street, direction, 15 m mark), weighted by how many rides are already in there. Nothing is ever overwritten.

    Widen coverage. A separate table holds one row per street and direction saying which stretch of it has ever been ridden — a start metre and an end metre. This run's reach is unioned into that row: the stored start moves down if this run began earlier, the end moves up if it finished later. That row is what tells the renderer where to stop drawing, so a half-ridden street gets a half-length line instead of a full one.

    Write an audit row. One row in session_segment_matches recording that this session contributed this run to this street and direction, with the first and last fix id. It is provenance, not model data: it is how the app can report that a ride matched 42 segments, how npm run prune-sessions finds rides that contributed nothing, and what a rebuild clears before replaying everything.

    Irreversible because the blend is a running mean — once a ride's numbers are averaged in, no subtraction takes them back out. Undoing a bad ride means npm run rebuild-model, which wipes the model and replays every session from its raw fixes.

D · Drawing the map

  1. The phone decides whether to ask

    Requests a box 20% wider than the screen; if the last one already covered it, no request is made.

  2. The server finds what has data

    Canonical segments in the box that have at least one bucket. Segments with no data are skipped — the network covers a city.

  3. The server builds the lines

    Clip to coverage, offset 4 m, compute slopes, emit colour stops. A "stop" is a point where the slope crosses a band boundary (e.g., from green "easy down" to yellow "easy up").

  4. The phone cuts them into pieces

    Between each pair of adjacent stops, the colour is constant. Draw one short line segment in that one colour. The reason: map libraries can draw a line and colour it all one way, but they can't colour one line with a gradient (smooth colour change). So we work around it by drawing many short segments, each one solid colour.

  5. Merge, never replace

    New responses are merged into what's already drawn, and a counter discards any response that arrives after a newer one. Both were added because lines visibly flickered during rides.
